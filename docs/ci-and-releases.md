# CI and releases

HttplibApp uses Forgejo Actions. The workflows are in `.forgejo/workflows/`:

| Workflow      | Trigger                           | Result                                                       |
|---------------|-----------------------------------|--------------------------------------------------------------|
| `ci.yml`      | Any push to a branch, any PR      | Unit tests and Conan package check. Nothing is published     |
| `release.yml` | By hand from Forgejo, on `main`   | Asks the increase, writes `VERSION`, commits, tags and uploads the recipe |

Both run in a `node:22-trixie` container (Debian 13, gcc 14, the same as the devcontainer; Node is needed by the
actions), on a runner with the `docker` label.

## A normal push (`ci.yml`)

Every push to any branch, and every pull request, runs these steps:

1. **Checkout** of the commit.
2. **Toolchain**: `build-essential`, `cmake` and Conan 2 (in a Python venv).
3. **Conan cache**: `~/.conan2/p` is restored between runs (Botan and Catch2 are not built again: Botan takes a while). The key
   is the hash of `conanfile.py`.
4. **Conan profile**: `conan profile detect`.
5. **Unit tests**: the same commands as in local:
   ```bash
   conan install . --build=missing -s compiler.cppstd=20 -o build_tests=True
   cmake --preset conan-release
   cmake --build --preset conan-release
   ctest --preset conan-release --output-on-failure
   ```
6. **Conan package**: `conan create . --build=missing -s compiler.cppstd=20` builds the package with the default
   options (shared library) and runs `test_package/`: a small program that finds, links and loads
   `libHttplibApp.so`, as a consumer would.

A failure in any step marks the commit as failed. **Nothing is uploaded**: a normal push never publishes anything,
in any branch (including `main`).

## Versioning

### Where the version is

The version is written in **one place only**, the `VERSION` file at the root of the repository, with just
`MAJOR.MINOR.PATCH`:

```
0.1.0
```

A plain file, because CMake, Conan and the CI read it without any parser. Everything else is derived from it:

| What                    | How                                                  | Example (0.1.0)              |
|-------------------------|------------------------------------------------------|------------------------------|
| CMake project version   | `CMakeLists.txt` reads it before `project()`         | `PROJECT_VERSION`            |
| Conan package version   | `set_version()` in `conanfile.py` reads it           | `httplibapp/0.1.0`          |
| Shared library file     | CMake `VERSION`                                      | `libHttplibApp.so.0.1.0`     |
| SONAME (ABI version)    | CMake `SOVERSION` (see below)                        | `libHttplibApp.so.0.1`       |
| Git tag                 | Created by the release workflow                      | `v0.1.0`                     |
| Release commit          | Created by the release workflow                      | `Release v0.1.0`             |
| Compile time macros     | `HttplibAppVersion.h`, generated by CMake            | `HTTPLIBAPP_VERSION "0.1.0"`   |
| Run time                | `getLibraryInfo()`, compiled into the library        | `getLibraryInfo().version`   |

CMake and Conan reject a `VERSION` that is not `MAJOR.MINOR.PATCH`, and `conan create --version X` fails if `X` is
not the `VERSION` file.

`project()` also has the `DESCRIPTION`, which `HTTPLIBAPP_DESCRIPTION` and `getLibraryInfo()` report.

### Library information

- **Compile time**: `HttplibApp/HttplibAppVersion.h` (generated by CMake) defines `HTTPLIBAPP_NAME`,
  `HTTPLIBAPP_DESCRIPTION`, `HTTPLIBAPP_VERSION` and `HTTPLIBAPP_VERSION_MAJOR` / `_MINOR` / `_PATCH`: the version the
  program is compiled with.
- **Run time**: `ipb::http::getLibraryInfo()` (`HttplibApp/LibraryInfo.h`) returns a `LibraryInfo` with the same
  data, compiled into the library, plus its `buildDate` (`"YYYY-MM-DD HH:MM:SS"`, local time of the machine that
  built it). It is the library that is loaded: with the shared library it may differ from `HTTPLIBAPP_VERSION` (a
  newer patch installed without recompiling the program).

```cpp
const ipb::http::LibraryInfo &lib = ipb::http::getLibraryInfo();
std::cout << lib.name << " " << lib.version << ", built " << lib.buildDate
          << " (compiled with " << HTTPLIBAPP_VERSION << ")\n";
```

The fields of `LibraryInfo` are part of the ABI: adding one is an incompatible change.

### Numbering: `MAJOR.MINOR.PATCH`

The version follows [Semantic Versioning](https://semver.org), applied to the **public API and the ABI** of the
shared library: what the installed headers (`include/HttplibApp/`) declare, and the layout of their classes.

**From 1.0.0:**

| Increase  | When                                                                          | SONAME           |
|-----------|-------------------------------------------------------------------------------|------------------|
| `PATCH`   | Bug fixes. API and ABI unchanged                                              | Same             |
| `MINOR`   | New features, compatible: new functions, new `Config` options                 | Same             |
| `MAJOR`   | Incompatible changes: removed or changed functions, changed exported classes  | `.so.MAJOR` changes |

**Before 1.0.0 (now):** the API is not stable yet, so the minor version plays the role of the major one:

| Increase  | When                                                                          | SONAME                |
|-----------|-------------------------------------------------------------------------------|-----------------------|
| `PATCH`   | Bug fixes and compatible additions. The ABI is unchanged                      | Same (`.so.0.1`)      |
| `MINOR`   | Anything that breaks the API or the ABI                                       | Changes (`.so.0.2`)   |

That is why the SONAME is `libHttplibApp.so.0.MINOR` before 1.0 and `libHttplibApp.so.MAJOR` after it: two
versions with the same SONAME must be interchangeable without recompiling the program.

Changes that break the ABI even if the source still compiles: adding or reordering members of an exported class,
adding virtual functions, changing default arguments or inline functions in the public headers.

### Consumers: version ranges

A consumer can follow the compatible versions with a range:

```python
self.requires("httplibapp/[~0.1]")    # Before 1.0: >=0.1.0 <0.2.0
self.requires("httplibapp/[^1.2]")    # From 1.0: >=1.2.0 <2.0.0
```

## Creating a release (`release.yml`)

Nobody edits `VERSION` by hand: the release workflow increases it.

### Steps

1. Merge the changes into `main` and wait for the CI to pass.
2. In Forgejo: **Actions** > **Release** > **Run workflow**, on the `main` branch.
3. Choose the increase, with the numbering rules above:

   | Choice  | From 0.1.2 | Use it for                                                                          |
   |---------|------------|-------------------------------------------------------------------------------------|
   | `patch` | `0.1.3`    | Fixes (and, before 1.0, compatible additions). The default                          |
   | `minor` | `0.2.0`    | New compatible features; before 1.0, any change that breaks the API or the ABI      |
   | `major` | `1.0.0`    | Changes that break the API or the ABI (from 1.0). `1.0.0` itself marks a stable API |
   | `none`  | `0.1.2`    | Publish `VERSION` as it is: the first release (`0.1.0`), or a retry (see below)     |

4. The new version is in `main` (`Release vX.Y.Z` commit, by the user that started the release), with its tag
   `vX.Y.Z`, and in the Conan registry. Run `git pull` to get the commit.

### What the release workflow does

1. **Only from `main`**: started from another branch, it fails.
2. Checkout (with the tags) and toolchain, as in `ci.yml`.
3. **New version**: reads `VERSION`, increases it, and checks that its tag does not exist yet (with `none`, an
   existing tag is only accepted if it is on the current commit: a retry). Writes the new `VERSION`.
4. Conan profile, and the Conan remote `forgejo`: `<forgejo url>/api/packages/<repository owner>/conan`
   (`.../api/packages/Commons/conan`).
5. **Validation** with the new version: the unit tests, and `conan create` for the shared (default) and the static
   (`shared=False`) library, each one with its `test_package`.
6. **Commit and tag**: commits `VERSION` (`Release vX.Y.Z`), creates the annotated tag `vX.Y.Z`, and pushes both
   to `main` in one atomic push. If `main` has moved since the release started, the push is rejected and nothing
   is published: run it again.
7. **Upload**: `conan upload httplibapp/<version> -r forgejo --only-recipe`. It is the last step, so the registry
   never has a version without its commit and tag.

The release commit is pushed with the automatic token of the workflow, so it does not start the CI again (the
release has already run the same checks).

Only the **recipe and its sources** (`exports_sources`: `VERSION`, `CMakeLists.txt`, `cmake/`, `include/`, `src/`, `test/`)
are uploaded, **never binaries**: a C++ binary is only valid for the same compiler, standard library and flags, so
each consumer builds HttplibApp with its own toolchain. The recipe has `build_policy = "missing"`, so the
consumer does not need to pass `--build`: Conan builds it the first time and keeps it in its cache.

Forgejo also offers the source archive (`.tar.gz` / `.zip`) of every tag in the repository page.

### Required configuration in Forgejo

- Actions enabled in the repository, and a runner with the `docker` label.
- The workflow pushes to `main` with its automatic token: if `main` is a protected branch, allow the pushes of
  Forgejo Actions in the branch protection rule (or the release fails at the push, before publishing).
- Repository (or organization) secrets:
  - `CONAN_USER`: the Forgejo user that uploads the package.
  - `CONAN_TOKEN`: an access token of that user with the `write:package` scope.

  The workflow passes them to Conan as `CONAN_LOGIN_USERNAME_FORGEJO` / `CONAN_PASSWORD_FORGEJO`.

### Mistakes

- **The release failed before the push** (tests, packages, push rejected): nothing was changed or published. Fix
  the cause and run it again with the same choice.
- **The release failed at the upload** (registry down, wrong token): the commit and the tag are already in `main`.
  Fix the cause and run it again with `none`: it publishes the same version without increasing it.
- **A published version is wrong**: do not reuse the version. Publish a new one (`patch`, or `minor` if the fix
  changes the API). Uploading the same version again creates a new *recipe revision* in Conan: the consumers that
  already have the previous one in their cache keep using it (unless they run with `--update`), so two builds of
  "the same version" may differ.

## Using the published package

```bash
conan remote add forgejo https://<forgejo>/api/packages/Commons/conan
conan remote login forgejo <user> -p <token>    # Token with the read:package scope
```

```python
def requirements(self):
    self.requires("httplibapp/[~0.1]")
```

The library is shared by default; `-o "httplibapp/*:shared=False"` gives the static one. With the shared library
the program needs `libHttplibApp.so` at run time: run it with the Conan run environment
(`source conanrun.sh`, or the `VirtualRunEnv` generator), or deploy the library with the program.

Since only the recipe is published, any option works: the consumer builds HttplibApp with it. For example the TLS
backend, `-o "httplibapp/*:tls=wolfssl"` (or `openssl`). The CI and the release check the default (`tls=none`).
